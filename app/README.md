# IntelXe Manager

A macOS app for what otherwise takes Terminal: see the state of the machine and the driver, and install, repair, undo, uninstall and
update it, and do stages 2 and 4 of the install guide in the OpenCore EFI. It is a front end: `install.sh` and `efi.sh` from the package
do the work, so a change made here and one made in Terminal are the same change.

Released from 0.1.2 on (`IntelXe-Manager-VERSION.zip` on the release page; the install guide's step 3.1). The Driver page's
install was used on the test machine (the test builds before 0.1.2); the EFI page made stage 4 there on the EFI of its SSD. Not
used yet: *Undo* on a real EFI, *Use an EFI folder...* on a USB stick that then booted, and a whole install from a
fresh macOS.

**Setup assistant** (opens by itself until it has finished once; the Overview page opens it again): 1. OpenCore's
settings (stage 2), with *Also prepare Safari on the GPU* to turn Apple Secure Boot off in the same change
(`efi.sh --settings-safari-apply`); 2. the driver package; 3. `IntelXe.kext` and SSDT-ARCOFF in the EFI (stage 4, with
HybridPM.kext on a hybrid CPU); 4. a GPU test; 5. done, with extras: Safari on the GPU, Zink for Java games, HiDPI
sizes, the menu bar item and the check at login. When OpenCore recorded no boot path it lists the EFI partitions to
choose from.

The About window (app menu) has the version, the licences and the credits.

**macOS update guard** ([`docs/design/DESIGN-os-update-guard.md`](../docs/design/DESIGN-os-update-guard.md)): the
Overview page lists the macOS updates Software Update offers (its record in `/Library/Preferences`, or *Check now*)
with whether the installed release supports each (`install.sh --supports-macos`). For one it does not, it warns (also
in a banner and in the check at login): there would be no desktop on the Arc afterwards. For one it does, *Prepare*
runs `Resources/osupdate-guard.sh --prepare` as root: a root-owned copy of the installed release's package and a
one-shot LaunchDaemon. At the first start of the new macOS that daemon checks the kexts, the Metal driver, the
system-volume copy and the boot guard, runs the kept package's `install.sh --apply` when something is missing and the
release supports the new macOS, restarts once, and removes itself (three tries at most, 14 days of waiting at most);
the page shows its result, the Report collects its log. Nothing is parked before the update (the design note says
why). Without a preparation the page still notices a new macOS build at the next start and shows what is missing.

**Game mode** ([`docs/design/DESIGN-game-mode.md`](../docs/design/DESIGN-game-mode.md)), off unless turned on, and
off again at every start of the app: while a game (an app in the games category, or one added from the menu bar
item) is in front, the GPU's lowest clock goes up (2400 MHz by default, through `debug.intelxe.slpc_min` and step
17), and optionally a running Time Machine backup is stopped. A root helper started once through the password
dialog does it and puts it back when the game leaves the front, when game mode is turned off, when the app ends or on
a signal. The menu bar item shows the state and turns it on and off.

After an install the app compares the EFI's `IntelXe.kext` with the package's (executable and `Info.plist`, byte for byte). It
warns only when they differ, the kext or its `Kernel > Add` entry is missing or off, or the EFI could not be read (then it says
"could not be checked", not "update it").

### The EFI page

`efi.sh` decides what changes; the app shows it. **Which EFI:** OpenCore's NVRAM variable
`4D1FDA02-38C7-4A6A-9CC6-4BCCA8B30102:boot-path` names the partition it booted from, which `diskutil` resolves by its
partition UUID; disk numbers are never used, they change between boots. OpenCore writes that variable only when
`Misc > Security > ExposeSensitiveData` includes 1 (`efi/sample-z790` has 6, without it): then the page lists the EFI
partitions with their disk's name and size to choose from, remembers the choice by UUID, and the stage-4 change adds 1
to `ExposeSensitiveData` so that the next boot records it.
**Use an EFI folder...** works on a folder you pick instead (a USB stick's `EFI` folder, or the folder holding it):
`efi.sh --efi`, with backups under `efi-backups/folder-<hash of the path>/`; on Windows, `windows/IntelXe-EFI.ps1` does the same.

**Every write** shows the disk (name, internal or external, size, device, partition UUID) and efi.sh's plan, line by
line, then asks; the password dialog follows. The app passes the plan's SHA-256 with the command, and efi.sh writes
nothing if the EFI no longer gives that plan. Before a change efi.sh copies the whole EFI folder to
`/Library/Application Support/intel-gpu-macos-driver/efi-backups/<partition UUID>/<NNN-date>/`; **Undo** puts back,
from the newest backup, only the files that change touched (`config.plist`, `IntelXe.kext`, `SSDT-ARCOFF.aml`,
`HybridPM.kext`), and
each undo goes one change further back.

- **Stage 4:** copies `IntelXe.kext` when it is missing or differs, adds or enables its `Kernel > Add` entry (and turns
  off an earlier `B580.kext` entry), copies `SSDT-ARCOFF.aml` and adds or enables its `ACPI > Add` entry. The table
  must name the card's upstream port as `ioreg` shows it (`\_SB.PC00.PEG1.PEGP` for the shipped one); with another path
  efi.sh writes that path into a copy of the table ("adapted to this card's port"). An `SSDT-ARCOFF.aml` of your own
  that names the port is kept. On a 12th-14th gen hybrid Intel CPU it also copies `HybridPM.kext` with an entry right
  below `Lilu.kext`'s; without Lilu in the EFI it leaves HybridPM out with a note.
- **Stage 2 (separate button):** `csr-active-config` with at least `0x803` (a wider value stays), `amfi_get_out_of_my_way=0x1`
  and `intelxe_surfvram=2` added to the boot-args (the rest kept), `csr-active-config` and `boot-args` in
  `NVRAM > Delete`, `ResizeAppleGpuBars = 10`, `DisableIoMapper = true`, `ReconnectGraphicsOnConnect = false`.
- `config.plist` is edited with `plutil` on a copy, written back as XML and checked with `plutil -lint` before it
  replaces the EFI's. The values are kept; dictionary keys come out in plutil's (alphabetical) order.
- Nothing for stage 1: installing macOS needs another machine or the USB installer.

Changes go through the macOS administrator password dialog (`osascript ... with administrator privileges`); there is no helper tool and
nothing stays running, but game mode's helper while game mode is on and the update guard's one-shot daemon after a
*Prepare*. A download is compared with the `.sha256` file of the same GitHub release. That finds a damaged file, it does
not prove who made the release. Files go to `~/Library/Application Support/IntelXe Manager`. It contacts only GitHub, and sends no data
(the Report page only opens the issue form in the browser).

English and Turkish, following the system language (`Resources/`).

## Building

`app/build.sh OUTDIR` needs the Command Line Tools and gives a universal, ad-hoc signed `IntelXe Manager.app`. `@State` is avoided, because
on the macOS 27 SDK it is a macro and the Command Line Tools have no SwiftUI macro plugin.

## Testing without the card

- `IntelXeManager --selftest [PACKAGE] [--snapshot FOLDER]`: version comparison, hash list, quoting, a release as GitHub sends it, the facts
  read from this machine, the package's `--status` and `--check`, and a PNG of each page.
- `release/test-install-flow.sh PACKAGE`: `install.sh` through install, damage, repair, undo and uninstall, in a throwaway root, with `kmutil`
  and the root checks stubbed. It does not test the real kernel collection step.
- `release/test-efi-flow.sh [PACKAGE]`: `efi.sh` against a fake EFI folder made from `efi/sample-z790/config.plist` as stage 1 leaves it:
  status, plans, apply, settings, undo, the plan hash, the ACPI path check, the boot-path and `ioreg` parsing. No root, no partition.
- With a package, `--selftest` also runs efi.sh through the app's own functions against a fake EFI (plan, hash, apply, the notice after
  an install, undo), and `--snapshot` adds the EFI page. Not tested without the real machine: OpenCore's `boot-path` on a real boot,
  mounting a real EFI partition, the password dialog, and `ioreg` with a real card.
- `app/tests/test-osupdate-guard.sh`: the update guard through preparation and the starts after minor and major
  updates (repair, restart, bounded tries, expiry, the boot guard, a damaged package) against a throwaway root, with a
  package made from `release/templates/install.sh` and `kmutil`, `nvram` and `shutdown` stubbed.
- `app/tests/test-gamemode-helper.sh`: game mode's helper against a throwaway root with `sysctl` and `tmutil` stubbed.
- `--selftest` also reads XeProbe's results lines, and with a package sets and removes the XeProbe boot-arg on the
  fake EFI through the plan's hash; `--snapshot` adds the Probe page as on a Lunar Lake laptop after a failed stage 3.
  Not tested without the hardware: the stage runs (`sysctl` as root), IOKit's GPU list on an Intel machine, the record
  of a stage the Mac never came back from.
- `IntelXeManager --gputest` / `--longtest` run the Tests page's GPU tests in Terminal (they need the card).
